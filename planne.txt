Step 1 — graph/state.py

We created graph/state.py to define the shared state of the StatAgent workflow. The state acts as the agent’s shared memory, allowing different LangGraph nodes such as the Planner, Investigator, Critic, and Report Generator to communicate with each other and preserve information throughout the investigation.

The state contains the user’s question and dataset path, the dataset profile, the investigation plan, the current and completed tasks, analysis results, generated Python code, execution errors, critic feedback, evidence sufficiency, the final report, and the current iteration number.

We used TypedDict because it provides a clear structure for the dictionary used as our workflow state while keeping the implementation lightweight. We used total=False because all fields are not available at the beginning of the workflow. For example, the question and dataset path exist initially, while the dataset profile, investigation plan, analysis results, critic feedback, and final report are generated later by different nodes.

The important fields are:

question: stores the original business/statistical question.
dataset_path: stores the location of the dataset.
dataset_profile: stores information discovered during dataset profiling, such as rows, columns, data types, missing values, and duplicates.
investigation_plan: stores the investigation steps decided by the Planner Agent.
current_task: stores the analysis currently being performed.
completed_tasks: stores previously completed investigations to avoid unnecessary repetition.
analysis_results: stores the results returned by statistical analysis tools.
generated_code: stores Python code generated by the LLM when custom analysis is required.
execution_error: stores errors produced when generated Python code fails.
critic_feedback: stores feedback from the Critic Agent about the quality or sufficiency of the evidence.
evidence_sufficient: determines whether the system has enough evidence to generate the final report or needs further investigation.
final_report: stores the final evidence-backed analytical report.
iteration: tracks how many investigation cycles have been completed and can be used to prevent an infinite loop.

The main idea is:

User Question → State → Planner → State → Investigator → State → Critic → State → Final Report

Without a shared state, we would have to manually pass many variables between every function or agent. As the workflow becomes more complex, this would make the system harder to maintain and would make iterative investigation more difficult.

Alternative approaches include using a normal Python dictionary, a dataclass, or a Pydantic model. A normal dictionary is simpler but does not clearly define the expected structure. A dataclass provides stronger structure and is useful for conventional Python applications. Pydantic provides runtime validation and is useful when strict data validation is required. We chose TypedDict because our current LangGraph workflow mainly needs a lightweight, clearly defined shared state.

The most important concept to remember is:

State = the agent’s investigation notebook.

The Planner writes the investigation plan, the Investigator adds analysis results, the Critic adds feedback, and the workflow uses this information to decide what should happen next.

The evidence_sufficient and iteration fields are particularly important because they will later allow StatAgent to behave autonomously:

Evidence sufficient → generate the final report.
Evidence insufficient → perform another investigation.
Maximum iterations reached → stop the investigation safely.

This state will become the backbone of the entire StatAgent architecture.
Step 3 — agents/planner.py — Planner Agent
What did we build?

We created agents/planner.py, which contains the Planner Agent of StatAgent.

The Planner Agent receives two important inputs:

The user's business/statistical question.
The profile of the uploaded dataset generated by tools/profiler.py.

It then uses an LLM to create a question-specific investigation plan.

The current workflow is:

User Question
      +
Dataset Profile
      ↓
  Planner Agent
      ↓
Investigation Plan

For example, when the user asks:

"What factors are associated with passenger survival?"

and the dataset contains columns such as Survived, Sex, Pclass, Age, Fare, etc., the Planner generates a plan involving descriptive analysis, group comparisons, hypothesis testing, visualization, and potentially multivariate analysis.

The Planner does not perform the statistical calculations itself. Its job is to decide what should be investigated.

Why did we build the Planner Agent?

A normal automated EDA system could run a fixed list of analyses every time:

Missing values
      ↓
Descriptive statistics
      ↓
Correlation
      ↓
Outliers
      ↓
Plots

This approach is easy to build, but it is not truly question-driven.

StatAgent is supposed to investigate a specific question, so the analysis should depend on the question.

For example:

Question:
"What factors are associated with passenger survival?"

requires different analysis from:

Question:
"Why did revenue decrease in Q3?"

The Planner allows the system to dynamically determine which investigations are relevant.

Therefore:

Planner Agent = decides what needs to be investigated.

What exactly did we implement?

We created a ChatGroq LLM:

llm = ChatGroq(
    model="openai/gpt-oss-120b",
    temperature=0
)

We use the Groq-hosted LLM to perform the planning/reasoning.

We then created a ChatPromptTemplate containing instructions for the Planner.

The Planner is told to:

Understand the user's question.
Use the dataset profile.
Create a sequence of analytical tasks.
Only use columns actually available in the dataset.
Avoid inventing columns.
Prefer statistical/data-driven investigations.
Break complex questions into smaller tasks.
Avoid unnecessary analysis.
Return an investigation plan.

The function:

create_investigation_plan(
    question,
    dataset_profile
)

takes the question and profiler output and sends them to the LLM.

The result is the investigation plan.

Why do we give the Dataset Profile to the Planner?

The Planner should know what information actually exists in the dataset.

For example, suppose the user asks:

Why did sales decrease in Q3?

but the uploaded dataset contains:

PassengerId
Survived
Pclass
Name
Sex
Age
Fare

There is no sales variable or relevant time variable.

The Planner should not invent a Sales or Quarter column.

When we tested this, the Planner correctly recognized that the dataset did not contain the information required to investigate a sales decline and recommended obtaining an appropriate dataset.

This is an important property of our system:

Dataset Profile
      ↓
Planner
      ↓
Analysis based on actual available data

rather than:

Question
   ↓
LLM assumes columns
   ↓
Hallucinated analysis
What happens if we don't provide the Dataset Profile?

The LLM may make assumptions about the dataset.

For example:

User:
Why did revenue decrease?

LLM:
Analyze revenue by region, product, quarter...

But what if the dataset doesn't contain:

revenue
region
quarter

The generated plan would be unusable.

Providing the dataset profile gives the Planner actual knowledge of the dataset structure.

Why doesn't the Planner perform the calculations?

We deliberately separate reasoning from computation.

The LLM should decide:

"Perform a chi-square test between Sex and Survived."

But Python should calculate:

Chi-square statistic
p-value
degrees of freedom

The architecture is therefore:

LLM
 ↓
Decision
 ↓
Python Statistical Tool
 ↓
Actual Calculation
 ↓
LLM
 ↓
Interpretation

This reduces the possibility of the LLM inventing statistical values.

The principle we are following is:

LLM decides what to do; Python performs the actual computation.

Why did we use temperature=0?

We used:

temperature=0

because the Planner performs a structured planning task.

We want the model to be relatively consistent and focused rather than unnecessarily creative.

For example, we don't want the same question to randomly produce completely different investigation strategies every time.

Temperature 0 does not guarantee identical output in every possible situation, but it reduces randomness.

Why did we use ChatPromptTemplate?

The Planner needs dynamic information:

User Question
+
Dataset Profile

Therefore, instead of hardcoding one question, we use variables:

{question}
{dataset_profile}

This allows the same Planner to work with different questions and datasets.

What happens if we don't have a Planner?

We could use a fixed EDA pipeline:

Dataset
 ↓
Missing values
 ↓
Descriptive statistics
 ↓
Correlation
 ↓
Outliers
 ↓
Plots
 ↓
Report

The problem is that every question would receive essentially the same analysis.

For example:

Question:
"Does gender affect survival?"

doesn't necessarily require every possible EDA operation.

The Planner allows us to create a targeted investigation:

Question
 ↓
Compare survival by gender
 ↓
Calculate survival rates
 ↓
Chi-square test
 ↓
Evaluate evidence

This makes the system more autonomous and question-driven.

Important observation from our test

When we tested the Planner with a Titanic dataset and asked:

"What factors are associated with passenger survival?"

the Planner generated a detailed investigation plan including:

Missing-value investigation.
Categorical and numerical variable analysis.
Descriptive statistics.
Chi-square tests.
t-tests/Mann-Whitney U.
Visualization.
Logistic regression.
Multicollinearity analysis.
Model evaluation.
Final evidence-based summary.

This demonstrated that the Planner can transform a high-level question into a multi-step statistical investigation plan.

However, the Planner's output should not automatically be treated as correct.

Later components will decide:

Is this analysis actually necessary?
        ↓
Can we execute it?
        ↓
Are the results valid?
        ↓
Is there enough evidence?

That is why we need the Investigator and Critic components.

Important limitation of the current Planner

The current Planner returns a plain text numbered list.

For example:

1. Analyze survival by Sex.
2. Analyze survival by Pclass.
3. Perform chi-square test.

This is readable for humans but not ideal for an automated system.

Later, we should convert the Planner output into structured data, for example:

{
    "analysis": "chi_square",
    "feature": "Sex",
    "target": "Survived"
}

This will make it much easier for LangGraph to determine which Python tool should be called.

We are intentionally not implementing this yet because first we want to establish the basic Planner behavior.

Key concept to remember

The easiest way to remember planner.py is:

The Planner answers: "What should I investigate to answer the user's question?"

It does not answer:

"What is the answer?"

and it does not perform the actual statistical calculations.

Our separation is:

Profiler
→ What is in the dataset?

Planner
→ What should we investigate?

Investigator
→ Perform the investigation.

Python Tools
→ Calculate the actual statistics.

Critic
→ Is the evidence sufficient and valid?

Report Generator
→ What does the evidence tell us?

Step 4 — tools/statistics.py — Statistical Analysis Tools
What did we build?

We created tools/statistics.py, which contains the deterministic statistical tools that StatAgent will use to perform actual calculations.

The Planner Agent decides what analysis should be performed, but the LLM should not calculate statistical values itself. Instead, the Investigator Agent will eventually call these Python functions to obtain reliable statistical results.

The current tools are:

descriptive_statistics()
group_analysis()
correlation_analysis()
hypothesis_test()

The overall architecture is:

User Question
      ↓
Planner Agent
      ↓
Investigation Plan
      ↓
Investigator Agent
      ↓
Statistical Tool
      ↓
Python / SciPy
      ↓
Actual Statistical Result
Why did we create separate statistical tools?

We could ask the LLM to generate and execute arbitrary statistical code for every task.

However, that would make the system less controlled and potentially unreliable.

Instead, we provide predefined statistical functions.

For example:

Planner:
"Check whether Sex is associated with Survival."

        ↓

Investigator:

hypothesis_test(
    df,
    test="chi_square",
    column="Survived",
    group_column="Sex"
)

        ↓

Python / SciPy

        ↓

Actual:
chi-square statistic
p-value
degrees of freedom

The LLM decides what to investigate, while Python performs the actual calculation.

The principle is:

LLM = decision-making and interpretation. Python = deterministic computation.

1. descriptive_statistics()

This function calculates basic descriptive statistics for a numerical column.

It returns:

count
mean
median
standard deviation
minimum
maximum
Q1
Q3

For example:

Age

Mean: 29.7
Median: 28
Std: 14.5
Min: 0.42
Max: 80
Why do we need it?

Before performing advanced analysis, we need to understand the basic characteristics of the data.

It helps answer questions such as:

What is the average?
How spread out is the variable?
Are there extreme values?
What is the range?
Is the distribution potentially skewed?
What happens if we don't do it?

The agent may perform advanced statistical analysis without understanding the underlying variable.

For example, it could run a statistical test without knowing that the variable has extreme values or substantial dispersion.

2. group_analysis()

This function calculates statistics for groups.

Example:

Average Fare by Passenger Class

Pclass 1 → 84.15
Pclass 2 → 20.66
Pclass 3 → 13.68

The function calculates:

count
mean
median

for each group.

Why do we need it?

Many business and statistical questions involve comparisons between groups.

Examples:

Revenue by region
Salary by department
Survival by passenger class
Sales by product category
What happens if we don't do it?

The agent would have difficulty investigating relationships between categorical variables and numerical outcomes.

3. correlation_analysis()

This function measures the relationship between two numerical variables.

We support:

Pearson correlation
Spearman correlation
Pearson

Measures the strength of a linear relationship.

Example:

Age ↔ Fare
Spearman

Measures a monotonic relationship based on ranks and can be more appropriate when the relationship isn't well described by a linear model or when robustness to distributional assumptions is desirable.

The function returns:

correlation coefficient
p-value
sample size
method

Example:

Correlation: 0.32
p-value: 0.001
Why do we need it?

It allows StatAgent to investigate whether numerical variables are related.

For example:

Does discount relate to revenue?

Does advertising spend relate to sales?

Does age relate to fare?
What happens if we don't do it?

The agent loses an important tool for investigating relationships between numerical variables.

4. hypothesis_test()

This is currently our most important statistical tool.

It supports:

Chi-square test
Independent t-test
Mann-Whitney U test
Chi-square test

Used to investigate whether two categorical variables are associated.

Example:

Sex ↔ Survived

The function creates a contingency table and performs the chi-square test.

It returns:

chi-square statistic
p-value
degrees of freedom
sample size
Example question

Is passenger sex associated with survival?

The agent can request:

hypothesis_test(
    df,
    test="chi_square",
    column="Survived",
    group_column="Sex"
)
Independent t-test

Used to compare the means of a numerical variable between two groups.

Example:

Age of survivors
vs
Age of non-survivors

The implementation uses Welch's t-test:

ttest_ind(
    group1,
    group2,
    equal_var=False
)

Using equal_var=False avoids assuming that the two groups have equal population variances.

Mann-Whitney U test

This provides a non-parametric alternative when the assumptions or distributional characteristics make a t-test less appropriate.

For example:

Age distribution of survivors
vs
Age distribution of non-survivors

The tool compares the two groups without relying on the same normality assumption as a t-test.

Why do we validate columns?

Each function checks whether requested columns actually exist.

For example:

if column not in df.columns:
    raise ValueError(...)
Why?

Because the LLM may select an invalid column.

For example:

LLM:
Analyze "customer_income"

Dataset:
No customer_income column

Instead of silently failing, the tool returns an explicit error.

Later, the Investigator/repair workflow can use this error to recover.

This is important for our future self-correction mechanism.

Why do we return dictionaries?

For example:

return {
    "test": "chi_square",
    "statistic": float(statistic),
    "p_value": float(p_value),
    "degrees_of_freedom": int(dof),
}

We use structured dictionaries because the results will eventually be stored in our LangGraph state:

analysis_results
        ↓
{
    test: ...
    statistic: ...
    p_value: ...
}

The Critic and Report Generator can then consume these results.

What happens if the LLM performs the statistics itself?

Suppose the LLM says:

"The correlation is 0.72 and p-value is 0.003."

There is no guarantee that those numbers were actually calculated from the dataset.

The LLM is a language model, not a reliable numerical computation engine.

Our architecture avoids this:

LLM
 ↓
Choose analysis
 ↓
Python
 ↓
Calculate
 ↓
Actual result
 ↓
LLM
 ↓
Interpret result

This is one of the core design principles of StatAgent.
